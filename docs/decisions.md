## D34 产品形态转为纯 PC 游戏（2026-10-15）

- **背景**：产品方向由「AI 对战观赏台」确定为**纯 PC 游戏**：人可入座与 LLM 玩家同桌对抗、
  也可纯观战；后续扩展阿瓦隆等游戏；有上 Steam 计划；开发成本不作约束。
- **决策**：产品形态 = 纯 PC 单机游戏（入座/观战双模式），对手保持 LLM 驱动；
  引擎按 [D29](backend/00-overview.md) 的 headless 内核不动，入座在 `flow` 层加**人类座位
  显式分支**（推翻 D1「人不入局不操控」的观赏台定位，D29 的引擎范围声明同步扩展）；
  节奏控制（暂停/倍速/逐帧）从 roadmap 暂缓项转为必备。架构定案见
  [pc-game.md](pc-game.md)。
- **备选**：保留纯观战形态——否决，已明确要人入座；改用脚本 AI 对手——否决，已明确采用
  LLM；整体换游戏引擎（Godot/Unity）重写——否决，prompt 六层/LLM 网关/事件溯源是 Python
  资产，换引擎等于全部重写且失去单步调试性（P1 初衷）。
- **影响**：新增 [pc-game.md](pc-game.md) 架构分册；「重建最小 API」（roadmap）并入 PC
  游戏客户端方案；导出/静态复盘能力保留为离线回放路径。

## D35 双进程架构：Electron 客户端 + Python sidecar 引擎（2026-10-15）

- **背景**：PC 化需要桌面壳；候选 pywebview / Electron / Godot / Unity，且要为上 Steam
  留余地。引擎是纯 Python（asyncio + aiosqlite），与 UI 生命周期诉求不同。
- **决策**：**双进程**——Electron 客户端（保留 `frontend/` Vue 展示框架）+ Python 引擎
  sidecar（PyInstaller 打包）；本机回环 WebSocket 通信 + 启动握手 token；直播帧 =
  展示文档的增量分解（沿用 [frontend.md](frontend.md) 第八节契约，观赛/复盘共用组件）；
  人类座位接入 = `flow.ask/speak` 处**显式 if 分支**，不引回 Driver/注册表抽象。
- **备选**：pywebview 进程内桥——否决，Electron 生态（Overlay/后续 Steam 集成）更成熟且
  不计成本；Godot/Unity 壳——否决（见 D34 备选），留作表现力升级时的备选内核，引擎与
  通信契约不动；单进程合并 UI 与引擎——否决，崩溃隔离与打包边界不清晰。
- **影响**：CLAUDE.md 定位与文档清单更新；前端恢复直播/建局路线（frontend.md 第八节由
  本方案接管实现）；引擎保持无游戏 UI 依赖、仍可 CLI 独立跑局与调试。

## D36 多游戏扩展口径：游戏成册分目录，不预设插件抽象（2026-10-15）

- **背景**：扩展阿瓦隆等游戏成为确定需求，需与 D32「不预设插件抽象」衔接——既不能回到
  GameDefinition/registry 的旧病灶，也不能把两套游戏规则揉进同一模块。
- **决策**：维持 D32 口径（不复活运行时注册表、不预设通用步进抽象）：**每游戏一册分
  目录**（`rules/flow/prompts/memory/present` 按游戏归目录），加游戏 = 加一册 + 一个直排
  flow；展示文档/直播帧加 `game` 标识，前端按游戏渲染对应桌面；第二游戏落地时按实际
  教训再抽共性，不提前设计。
- **备选**：现在先做通用插件框架——否决，D32 教训（只有一个游戏时抽象是纯成本）；
  全部游戏塞单模块——否决，模块边界规则（游戏语义限定五模块）在多游戏下会自我矛盾。
- **影响**：CLAUDE.md 规则 6 的模块边界表述在第二游戏启动时按分册扩展；板子仍是代码
  常量；建局配置 = 选游戏 + 选板子。

## D37 Steam 专项与范围裁剪（2026-10-15）

- **背景**：有上 Steam 计划，但云存档、成就、Deck 适配暂不实现，先收窄首发范围。
- **决策**：首发**不做** Steamworks 集成（云存档/成就/Deck Verified 全部暂缓）；仅保留
  两项余地——①双进程拓扑（崩溃隔离本就需要）；②本地数据集中单一目录（SQLite + exports +
  设置），将来接云存档 = 同步该目录。LLM 密钥方案 = **玩家自带 key**：设置界面输入、存
  OS 凭据管理器（DPAPI/Keychain），仍只经 `api_key_env` 注入，不进配置/不落库/不进日志/
  不进 trace。
- **备选**：首发内置或托管 key + 自建 relay 代理计费——暂缓，涉及平台合规与抽成，启动
  Steam 专项时再议；现在做成就事件观察者——否决，事件流天然支持观察者模式，不提前做。
- **影响**：客户端现不背 Steamworks SDK；三档实施分期见 [pc-game.md](pc-game.md) 第九节；
  与 D4/安全规则（CLAUDE.md 规则 4）的密钥口径完全一致。

## D38 历史决策压缩归档（2026-10-15）

- **背景**：PC 化（D34–D37）定案后，D1–D33 多为**已完成或已被推翻**的历史决策，约 300 行
  详情（含已删除的 TUI/SSE/插件系统/多板子时代的实现细节）挤占文档主体；用户要求压缩
  过去的历史信息，只保留当前生效口径。
- **决策**：D1–D33 压缩为文末**附录索引**（编号 + 一句话要点 +
  状态），完整原文保留在 git 历史（`git log -- docs/decisions.md` 可回溯）；文件头更新
  说明；新决策仍按 append-only 追加编号，索引表本身也不再改写。
- **备选**：原样保留——否决，历史细节已固化在 git 与各规格文档，正文应聚焦当前口径；
  直接删除——否决，索引表保留检索入口与「仍生效/已推翻」判定，避免后人重踩已否决方向。
- **影响**：decisions.md 主体收窄为 D34 起当前决策 + 附录索引；后续条目引用旧决策时
  改用「Dn（见附录索引）」表述。
